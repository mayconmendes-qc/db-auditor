# Assessment por tabela — contrato v1

O assessment é sempre identificado por `environment_id`, `audit_run_id`, `database`, `schema` e `table`. A API não substitui o run solicitado pelo mais recente. Runs em andamento ou sem a tabela retornam `404`; escopo/UUID inválido retorna `400`. Um run `partial_success` é aceito, mas a resposta marca `run.partial = true` e a UI alerta que dados ausentes não implicam ausência de problemas.

`GET /api/v1/environments/{environment_id}/runs/{audit_run_id}/databases/{database}/schemas/{schema}/tables/{table}/assessment` retorna `version: 1`, `run`, `table`, `summary` e `links`. A tabela inclui owner, classe da relação, partição, tamanhos, estimativas, PK, tablespace, persistence, storage parameters, RLS, comentário, contagens operacionais e scans. O resumo agrega contagens de estrutura, findings e segurança do mesmo run. O contrato contém apenas fatos persistidos do run; não consulta o ambiente auditado no momento da leitura.

O score estrutural da tabela usa a versão `structural-v1`, base 100 e fatores explícitos: tabela comum/partitioned parent sem PK (−20), índices inválidos (−15 cada, máximo −30), constraints não validadas (−10 cada, máximo −20) e fração de tuplas mortas acima de 20%/50% em amostra de pelo menos 1.000 tuplas (−10/−20). Partições filhas e foreign tables não recebem penalidade por PK ausente. O cálculo é limitado a 0–100 e usa exclusivamente snapshots do mesmo run, portanto não muda quando findings deduplicados são atualizados por runs posteriores. `summary.score_factors` decompõe a pontuação, `score_confidence` é 1 para run completo ou 0,75 para run parcial, e `score_version` permite evoluir a metodologia sem ambiguidade.

O score só é exibido quando `postgres.tables`, `postgres.columns`, `postgres.constraints` e `postgres.indexes` têm cobertura `success` para o database do run solicitado. Sem essa evidência (inclusive em runs antigos ou perfis que omitem coletores), `score` e `score_confidence` são `null`, `score_status` é `insufficient_coverage` e `score_missing_collectors` informa o que faltou. Ausência de dados não se transforma em nota 100. Este é o score estrutural exigido pela US-061; o score mais amplo por tabela, schema e database da US-066 continua planejado para a Sprint 18.

As coleções grandes são páginas separadas. `links.columns`, `links.constraints` e `links.indexes` apontam para as APIs de inventário existentes com `audit_run_id` explícito. `links.findings`, `links.grants`, `links.triggers`, `links.rls-policies` e `links.dependencies` aceitam `limit` (1–500, padrão 50) e `offset` e retornam `{items,page}`. A lista de findings da tabela lê `finding_event` com `event_type=observed` daquele `audit_run_id`, então um run antigo continua mostrando o que aquele run viu mesmo que o finding corrente tenha sido suprimido ou regravado. A fila aberta da UI segue o estado deduplicado. Um run `partial_success` não resolve finding por ausência.

`links.graph` retorna `{nodes,edges,truncated}` para as FKs diretamente ligadas à tabela. O parâmetro `limit` aceita 1–100 (padrão 50). A projeção não expande além da profundidade 1, usa somente o mesmo database e run, e é encerrada após três segundos. Ausência de FK produz um grafo com apenas o nó central.

O coletor de grants considera privilégios efetivos de roles com login (`has_table_privilege`, incluindo herança e PUBLIC). Não armazena senha, ACL textual ou conteúdo de linhas. O coletor de dependências usa `pg_depend` para views, materialized views e funções; SQL dinâmico em funções não é inferido. Ambos executam somente leitura nos perfis manual e monthly. Policies de RLS são persistidas em `rls_policy_snapshot`; `policy_snapshot` continua reservado às policies TimescaleDB. Comentários de tabela e coluna são metadados de catálogo; podem conter informação inserida por administradores e devem ser protegidos por RBAC antes de acesso multiusuário (Sprint 20).

O projeto ainda não possui autenticação/RBAC. O contrato foi isolado por escopo, mas autorização por usuário é trabalho da Sprint 20; não exponha esta API a usuários não confiáveis antes disso. Nenhuma recomendação executa DDL ou DML no alvo.
